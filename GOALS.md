# Condizioni `/goal` per fase

`/goal` valuta la condizione con un modello piccolo che **legge solo la
conversazione**: non esegue comandi e non apre file. Quindi ogni condizione
deve nominare il comando che la dimostra, perché l'evidenza arrivi nel
transcript. Una condizione come "il refactoring è completo" è invalutabile.

Regole generali:

- Un `/goal` per volta, una fase per volta.
- Sempre con un tetto (`or stop after N turns`), altrimenti un loop bloccato
  gira finché non te ne accorgi.
- Sempre con i vincoli: senza, il modo più rapido di soddisfare la condizione
  è indebolire ciò che la verifica.
- `/goal clear` per fermarlo. `/clear` lo rimuove insieme alla conversazione.

## Fase 0 — rete di sicurezza

```
/goal npm run test:contract and npm run test:e2e both exit 0, every endpoint
listed in docs/contracts/ocaml-api.md has at least one golden-file test
including an invalid-input case, both React pages have Playwright screenshot
baselines at 375/768/1440, and the commands are documented in CLAUDE.md.
Constraints: tests assert current behaviour even where it looks wrong, each
such case is marked CHARACTERIZATION and listed in NOTES.md; no application
code is modified. Report the full test output each turn. Stop after 25 turns.
```

## Fase 1 — contratti

Meglio senza `/goal`: sono due task esplorativi one-shot, e un loop non serve.
Lanciali direttamente, in parallelo:

```
@"ocaml-reader (agent)" estrai il contratto completo dell'API Dream
@"django-archaeologist (agent)" estrai lo spec dell'admin
```

Poi rivedi tu i due documenti prima di andare avanti. Sono il fondamento di
tutto il resto: un errore qui si propaga silenziosamente in TypeScript e in Go.

## Fase 2 — migrazione frontend (un modulo per volta)

```
/goal src/components/<Nome>.tsx exists with no .jsx counterpart, tsc --noEmit
exits 0 for the whole project, npm run test:e2e exits 0 with zero updated
screenshot baselines, and no new `any` or @ts-ignore appears in the diff.
Constraints: only this module and its direct imports change; no visual or
behavioural change of any kind; no screenshot baseline is regenerated; user
visible strings are byte-identical. Show the diff and the full test output each
turn. Stop after 15 turns.
```

Ripeti per ogni modulo cambiando il nome. Noioso, ma è l'unico modo per cui
"nessun cambiamento visivo" resta verificabile: un loop su venti file rende
impossibile capire quale ha rotto una baseline.

## Fase 3 — baseline dello schema

Senza `/goal`: sono tre comandi, ma uno è `tern override-version` su un
database con dentro tutti i dati. Backup, prova su una copia ripristinata,
verifica, poi il database vero. A mano, guardando.

## Fase 4 — login compatibile con Django

```
/goal go test ./auth/... exits 0 and covers, with fixtures generated by Django's
make_password: every algorithm present in auth_user, at least two different
PBKDF2 iteration counts, a password with accents and a trailing space, an empty
password, a hash with the unusable-password `!` prefix, a truncated hash, and a
non-numeric iteration field. Constraints: no password, hash, salt or token
appears in any log, test name, report or committed fixture derived from real
data; every secret comparison uses crypto/subtle; both is_active and is_staff
are checked; iteration counts are read per row and never hardcoded. Show the
full test output each turn. Stop after 25 turns.
```

Poi, prima di considerarla chiusa: un account di prova reale, con password nota,
che fa login davvero. I test vector dimostrano l'algoritmo; solo una riga vera
dimostra che hai letto la colonna giusta nel formato giusto.

## Fase 5b — backend Go

```
/goal go vet ./... and golangci-lint run and go test ./... all exit 0, and
every validation rule in the <screen> section of docs/contracts/django-admin.md
has a corresponding table-driven test case, including the rules marked [DJANGO
DEFAULT]. Constraints: no DDL is written or applied; no shared table is altered;
no test is skipped or its assertions loosened. List each spec rule with the test
that covers it, and show the full test output each turn. Stop after 30 turns.
```

## Fase 5c — app di backoffice (in parallelo alla 5b)

Prima di tutto lo scheletro, una volta sola: progetto Vite + TanStack, `base`
`/bo/`, basename del router, build di produzione servita sotto `/bo` dietro
NGINX con il `try_files`. Verifica a mano che un reload su un path profondo
funzioni. È l'unica cosa che, sbagliata, si scopre solo in deploy.

Poi, una schermata per volta:

```
/goal the <screen> exists in the backoffice app, tsc --noEmit exits 0, and its
Playwright spec passes against the production build served under /bo, covering:
a successful save, every validation failure from docs/contracts/django-admin.md
with the message attached to the correct field, an inline row added and removed,
a delete with its cascade confirmation, and the keyboard-only path from first
field to save. Constraints: field order, grouping, labels and help text match
the spec verbatim in Italian; save-and-add-another and save-and-continue are
implemented; a failed save preserves the typed data; no file outside the
backoffice app is modified. Show the full test output each turn. Stop after 20
turns.
```

Poi provala tu a mano, inserendo due record da tastiera. È l'unica verifica che
dice se il rimpiazzo è più lento dell'admin, e nessun test la sostituisce.

## Verifica finale di fase

`/goal` non basta: l'evaluator legge la conversazione, cioè i resoconti
dell'agente che ha fatto il lavoro. Prima di chiudere una fase, lancia la
review indipendente:

```
@"refactor-reviewer (agent)" verifica la fase <N> contro i contratti
```

Questo è il pezzo che in OMC fa Ralph con l'agente `architect`, e che `/goal`
da solo non ha.

## Nota sui permessi

In Manual mode Claude chiede conferma prima di ogni comando non già consentito,
quindi il loop si ferma a ogni turno. Per un `/goal` che gira da solo serve auto
mode.

Attenzione però: «amatoriale» non vuol dire «senza dati veri». Questo progetto
ha un database con dentro i dati, gli upload degli utenti e gli account con le
loro password. Quindi:

- Auto mode sì per il lavoro sul codice — migrazione del frontend, handler,
  test.
- Auto mode **no** per qualunque cosa tocchi il database reale o la directory
  dei MEDIA. Il baseline con `tern override-version`, le migration e gli
  esperimenti sull'auth si fanno a mano, guardando, su una copia ripristinata
  prima che sul vero.
- Un agent che gira in auto mode non dovrebbe avere in ambiente le credenziali
  del database di produzione. Se le ha, il tetto di turni non ti protegge da
  niente.
